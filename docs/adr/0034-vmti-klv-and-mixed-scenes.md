# ADR-0034: A second implementation of a binary standard

- Status: Accepted
- Owner: Karl (implemented by Claude Code)
- Date: 2026-09-04

## Context

ADR-0032 made the CoT encoder reach every field a real consumer maps; ADR-0033
let one scene be reported by several sensors. Both were about *text* on the
wire, and both were checkable by reading the output.

MISB ST 0903.6 (VMTI) is not. It is what a video motion-detection sensor
emits: a binary Local Set under SMPTE 336 KLV framing, with BER lengths,
BER-OID tags, nested sub-sets, a trailing checksum, and numeric fields packed
through ST 1201's IMAPB mapping. Adding it makes chaff a **second
implementation of a published binary standard**, and the first implementation
is a decoder somebody else maintains.

That is the whole risk, and it is worth stating precisely. When two
implementations of a text format disagree, the output looks wrong. When two
implementations of *this* disagree, the output looks **fine**: a mis-scaled
IMAPB value is a well-formed number of the right width in the right place,
carrying a different quantity. Nothing about the bytes says so. A consumer
decodes it without complaint and reasons about it confidently.

## Decision

### 1. Add the encoder, and treat the conformance gate as what licenses it

`formats/klv.py` encodes a standalone VMTI Local Set: BER-TLV framing, the
universal label, the ST 0903.6-119 checksum, VTarget packs with nested
VTracker and VObject sets, and an Ontology series. Stdlib only — BER is
arithmetic and so is IMAPB.

Nothing here is safe on inspection. It is safe because the consuming
repository's gate decodes what this produces and scores it. Change a range, a
length, or a tag and that gate is the only thing between the change and a demo
that lies quietly.

Locally, the IMAPB port is pinned against **reference vectors generated by the
other implementation** (`tests/test_klv.py`). That is the only check available
inside this repo that can catch a scaling error, because every wrong answer is
also a plausible one.

### 2. Absence is an omitted item

A Local Set says "not reported" by leaving the item out, so every optional item
comes from a column and is omitted when the row has none. Same rule ADR-0032
established for CoT, expressed in the vocabulary this format gives us. The
positional sigmas are all-or-nothing for the same reason: the 16-byte location
pack carries three, and a partial set would have to invent the rest.

### 3. Classification stays plural

ST 0903.6 §7.3 lets one target carry several competing labels, each with its
own confidence — the standard's own example hangs Vehicle 90%, Car 70% and
Motorcycle 50% off a single target. The encoder emits one VObject per
hypothesis a row states, and a hypothesis whose column is absent is simply not
asserted. Collapsing them to a winner is a loss no consumer can undo.

**The ontology IRIs come from the spec and are absent from this repository.**
They are the consuming system's vocabulary; a generator that shipped one
program's ontology would be carrying that program's domain knowledge in a
public tool. A test asserts the encoder's source contains none.

### 4. One packet per row

A VMTI frame legitimately carries many targets; this encodes one. That keeps
the streamed bytes identical to the whole-file bytes, keeps the encoder boring,
and a single-target frame is ordinary VMTI. Batching a tick's targets into one
frame is a real thing a sensor does, is not expressible on the per-record seam
that streaming uses, and is deferred rather than half-built.

### 5. An observer may choose its own format

`ObserverSpec.format` overrides the scene's. Two sensors watching one scene
need not speak the same language, and a consumer that fuses across a *format*
boundary — not merely across two feeds of one format — is the one worth
rehearsing against. `examples/correlated_multikind.json` renders one scene as
CoT XML and as VMTI KLV simultaneously.

Format and sink remain independent axes (INV-2). An observer picks which
encoder its own rendering goes through; it does not merge the axes.

## Consequences

All 21 attributes a real VMTI consumer declares are reachable, verified by
decoding the preset's 240 packets through that consumer: no refusals, no
anomalies, 21 of 21 attributes and 11 confidence entries.

**A bug this nearly shipped, recorded because the shape of it matters.** The
target-id fallback list did not include `target_id` — the name ST 0903.6 itself
uses and the one every spec here reaches for. Every target fell back to its
position in the packet, which for a one-target frame is always 1, so the whole
feed reported *one entity* over and over. Every packet was well-formed. Every
value was correct. Coverage was 21 of 21, because coverage does not depend on
identity. It was found by a test asserting two different ids produce two
different packets, and it is exactly the failure this ADR opens by describing.

**Known gaps.** No embedded-VMTI (the ST 0601 parent frame carrying a VMTI set
as one item) and no multi-target frames. A digit-only `id_pattern` loses
leading zeros, so `"0123"` and `"123"` become one target id — widen the pattern
rather than pad it.

**What this does not make chaff.** Not a conforming VMTI *system*: nothing here
satisfies the standard's requirement clauses about which items must be present
when, and it emits well-formed packets rather than a compliant transmit path.
